| Channel | Available customer workflows |
| --- | --- |
| Voice | Voice flows, campaign calls, inbound routing, separately configured AI agents, DTMF, audio playback, speech, forwarding, recordings, calls, and reports |
| SMS | Send an SMS from a supported flow using an available sender ID |
| WhatsApp | Manage templates and send an approved template from a supported flow |

<Warning>

---
title: "How Gomobile works"
description: "Learn how contacts, audiences, flows, campaigns, runs, and calls work together."
icon: "waypoints"
---

Most Gomobile workflows connect customer data to an automated experience, then produce activity that your team can investigate.

```mermaid
flowchart TD
    Contacts[Contacts] --> Audience[Audience]
    Audience --> Campaign[Campaign]
    Flow[Saved flow] --> Campaign
    Campaign --> Run[Run: flow execution]
    Run --> Activity[Calls, messages, or contact updates]
    Activity --> Results[Activity and outcomes]
    Results --> Report[Campaign report]
```

A campaign is the outreach program; a run is a flow execution. These docs use **Campaign** and **Run** to match the Gomobile interface. The flow is saved configuration, while the run records what happened when it executed.

See the [core concepts](/learn/concepts/organizations) and [architecture overview](/learn/architecture) for more detail.

## Core objects

| Object | What it represents | Example |
| --- | --- | --- |
| Contact | One customer identified primarily by phone number, with standard fields and optional custom attributes | Amina El Amrani in Casablanca |
| Audience | The contacts eligible for a campaign | Customers with a renewal date in the next 30 days |
| Flow | The automation Gomobile runs | Confirm an appointment and update the contact's status |
| Campaign | The audience, flow, schedule, channel resources, calling policy, and lifecycle for an outreach operation | October appointment confirmations |
| Run | One execution of a flow for a particular context | The automation created for Amina during the campaign |
| Call | A placed or answered voice interaction associated with a run when voice is involved | The outbound call to Amina |

## Static and live audiences

A **static audience** changes only when someone adds or removes contacts. It works well for a reviewed list, event attendees, or a one-time operational batch.

A **live audience** uses rules. Contacts enter and leave automatically as their data begins or stops matching those rules. Use it for continuously changing segments, such as customers whose renewal date is approaching.

You choose the audience type during creation and cannot switch the type later.

## Voice and multichannel flows

A **Voice flow** defines what happens during a call. The visual builder can play audio, say text, collect keypad input, record a segment, transfer or end the call, branch, connect to an AI agent, update the contact, apply a tag, or send a follow-up message.

A **Multichannel flow** coordinates actions outside a single call. It can branch, update contacts, apply tags, send SMS, send approved WhatsApp templates, and invoke a Voice flow as a sub-flow.

<Note>
  A campaign, flow test, API request, or inbound binding can start a run. Voice flows can connect to an active AI agent. Multichannel flows can invoke Voice sub-flows; Voice flows cannot invoke sub-flows.
</Note>

## Runs, calls, tries, and outcomes

- A **run** records how a flow progressed for one execution context.
- A **call** records a voice interaction and its timeline, result, and associated media when available.
- A **try** is one campaign attempt to reach a contact. Retries create additional tries.
- An **outcome** summarizes what ultimately happened for the contact or interaction.
- **In flight** means the activity can still progress. **Settled** means the activity meets the reporting view’s settlement rules; it does not guarantee that every child run or delayed artifact is complete.

Use the campaign report to understand the operation as a whole, Runs to investigate automation paths, and Calls to investigate voice details.

## Inbound routing

An **inbound binding** routes an available phone number to one AI agent or one Voice flow. Binding history separates reporting periods when a number's destination changes.

## Credits

A credit is Gomobile's prepaid usage unit. It is not a currency. Eligible users can see the organization balance, while calls, runs, and campaigns show applicable usage and cost breakdowns.

A channel is how an interaction reaches a customer. A flow defines the actions performed through those channels.

| Channel or flow type | Role | Required resource |
| --- | --- | --- |
| Voice | An in-call experience built with a Voice flow | Available caller number for outbound calls, or inbound binding for incoming calls |
| SMS | A supported message action within a flow | Available SMS sender ID |
| WhatsApp | An approved template action within a supported flow | Available WhatsApp connection and approved template |
| Multichannel flow | Coordinates supported messaging, conditions, contact changes, tags, and Voice sub-flows | Resources required by the actions reached |

## Resource versus action

A phone number, sender ID, or WhatsApp connection enables a channel. The flow action determines what to do with it. Having a resource does not automatically send a message or place a call.

## Choosing a flow

Use Voice for steps that happen during a call. Use Multichannel to coordinate work outside a single call, such as a condition followed by an SMS or a Voice sub-flow. The flow type cannot be changed after creation.

SMS and WhatsApp are supported flow actions; the application does not offer SMS-only or WhatsApp-only campaigns. Channel tests perform real activity and may consume credits.

---
title: "WhatsApp and templates"
description: "Understand the WhatsApp connection, template approval, and flow-based messaging."
icon: "message-circle"
---

WhatsApp in Gomobile combines an available WhatsApp Business connection with approved message templates. A template is reusable message content; a flow determines when to send it and which values to supply.

## Connection and templates

The organization needs an available WhatsApp channel before it can use messaging. In **WhatsApp**, review connection state and manage templates. Connection provisioning is separate from authoring a template.

A template contains its name, language, category, message body, and ordered variables, plus supported optional content such as headers, footers, or buttons. For an appointment reminder, variables can supply the customer’s name and appointment details.

## Approval lifecycle

| State | Meaning |
| --- | --- |
| Pending | Submitted for Meta approval |
| Approved | Available for supported sends and tests |
| Rejected | Review the rejection reason, edit, and resubmit |

Request a status refresh, then check the template list again after synchronization. Refresh is asynchronous; the immediate response can still show the previous status. Creating or submitting a template does not mean a message has been delivered.

## Sending in a workflow

Use an approved template in a supported flow. Supply the required variable values and review the destination. The API template test sends a real message to the organization creator’s verified phone number, using variable fallback values. It does not accept another recipient. A message ID does not prove delivery.

Resubmitting a rejected template replaces its revisable content. Include optional headers, footers, and buttons you want to keep. Deleting a template removes every language variant sharing its name on the connected channel.

The application does not provide a WhatsApp-only campaign or a general inbox experience. Build messaging into a supported flow instead.

Next: [Flows](/learn/concepts/flows), [WhatsApp reference](/developers/reference/whatsapp), and [responsible use](/product/responsible-use).

An AI voice agent defines a conversational assistant’s behavior. Unlike a flow, which follows authored steps and branches, an agent responds using its instructions and configured AI and voice capabilities.

## What you configure

Define the agent’s purpose and instructions, welcome message, and available voice setup. Give it a focused scope, such as answering questions about appointment preparation. A compatible [knowledge base](/learn/concepts/knowledge-bases) can provide supporting documents.

Available providers, models, voices, and controls depend on workspace configuration. Read the choices offered by Gomobile rather than assuming every option is available.

## Configuration versus publication

Creating an agent stores its configuration. Publishing it connects it to selected eligible phone numbers for inbound use. A caller reaching a bound number is routed to the agent.

Archiving or deleting can be blocked while an active campaign uses the agent. Resolve the dependency before retrying. Successful archiving or deletion disables its inbound bindings. Restoring it does not automatically republish it.

## Testing

A text playground tests response behavior, not the complete voice experience. After deliberate inbound publication, call a test number and check the greeting, spoken responses, and available activity. Tests and calls can incur usage.

Voice flows can connect to an active AI agent through the visual builder. Configure the available continuation paths and verify them with a controlled test. Agent Tools & Actions and Policies marked coming soon are not available workflows.

Review recording behavior before publication. The documented API publication path enables recording by default.

SHA256: 766259f6df22c369b27d92a9aa0a59d2d543e0505a31e7a6fc990d57526f761c

---
title: "Understand the campaign lifecycle"
description: "Learn how audiences enroll contacts and what launch, pause, resume, stop, and retries mean."
icon: "refresh-cw"
---

A campaign connects one audience to one saved Voice or Multichannel flow. Its schedule, calling policy, channel resources, and lifecycle determine when eligible contacts can progress.

## Before creation

Prepare and review the audience, flow, schedule, calling hours, phone numbers, retry plan, and credits. The campaign's audience and flow binding cannot be replaced after creation.

## Static and live enrollment

| Audience type | Campaign behavior |
| --- | --- |
| Static | The campaign starts from a snapshot of the audience membership used for the launch. Later manual membership changes do not redefine that original snapshot. |
| Live | Contacts can continue enrolling while the campaign is running when they begin matching the audience rules. |

<Warning>
  Check live-audience rules before launch. A later contact-data change can make another contact eligible for a running campaign and produce real channel activity.
</Warning>

## Lifecycle actions

| Action | What to expect |
| --- | --- |
| Save as draft | Stores the configuration without starting campaign activity. |
| Launch or schedule | Makes the campaign eligible to start at its configured time and within its calling policy. |
| Pause | Prevents new campaign work from starting. Work or retries already scheduled may still proceed depending on timing. |
| Resume | Allows an eligible paused campaign to start new work again. |
| Stop | Cancels pending campaign work. Calls already in progress may finish. |

The interface exposes only actions valid for the campaign's current state. Verify the status after each operation instead of assuming every queued or in-flight item changed immediately.

## Calling hours and schedules

Campaign contact initiation is scheduled against the configured calling hours. Work already taking place inside a live call can continue outside those hours. Calling hours do not provide a compliance guarantee. It can use the configured organization hours, custom campaign hours, or unrestricted operation when that option is permitted by your policy.

Campaigns retain the calling-hours configuration associated with them rather than automatically adopting later changes to the organization defaults. Review the displayed timezone before launch.

## Retries

Eligible voice campaigns can schedule additional tries. Keep all retry timing inside the campaign's active period and calling policy. A **try** is an attempt for one enrolled contact; it is not a separate campaign.

Pause and stop are not interchangeable: pausing is reversible, while stopping cancels pending campaign work. Because timing can affect already scheduled work, confirm actual retry behavior in a safe test campaign before using it operationally.

## Reporting levels

- Use **campaign results** to understand enrolled contacts, tries, outcomes, progress, funnels, and applicable usage.
- Use **Runs** to investigate the automation path and values for one execution.
- Use **Calls** to investigate one voice interaction, including its outcome, timeline, and any transcript or recording made available.

  </Step>
  <Step title="Store the secret immediately">
    Copy the secret into an approved server-side secret manager. Gomobile shows the complete value only once.
  </Step>
  <Step title="Acknowledge storage">
    Confirm that you copied the secret, then close the dialog.
  </Step>
</Steps>

<Warning>
  If you lose the secret, you cannot reveal it again. Create a replacement key, update the integration, verify it, and revoke the old key.
</Warning>

## Send the key

Send the secret in the `X-API-Key` header on every API request:

```http
X-API-Key: <your-secret-key>
```

Use the API base URL supplied by Gomobile, including the `/api` prefix. Available operations depend on the key’s role and your organization’s enabled services.

For copy-ready environment variables, pagination, error handling, and safe test guidance, see [API basics](/developers/api-basics).

## Manage the key lifecycle

From **API keys**, you can:

- search by name or masked identifier;
- see role, status, last use, creator, and expiration;
- change its name or expiration;
- disable it temporarily and enable it again;
- revoke it permanently.

The assigned role is fixed. Create a new key when the integration needs a different role.

## Rotate a key safely

<Steps>
  <Step title="Create a replacement">
    Give the new key a name that identifies the integration and rotation period.
  </Step>
  <Step title="Update the server secret">
    Replace the credential in the integration's secret manager without committing it to source control.
  </Step>
  <Step title="Verify requests">
    Confirm that the integration succeeds with the replacement key.
  </Step>
  <Step title="Revoke the old key">
    Revoke the previous credential only after all workloads have moved to the replacement.
  </Step>
</Steps>

## Authentication failures

| Symptom | Check |
| --- | --- |
| Request is unauthenticated | The header is exactly `X-API-Key`, the value is the secret, and the key has not been revoked |
| Request was working and now fails | Check whether the key expired or was disabled |
| Request is forbidden | Check the key’s role and your organization’s enabled services |
| Secret cannot be recovered | Create a replacement; the complete secret is shown only at creation |

Gomobile's API is an organization-scoped JSON API for server-to-server integrations. Except for file uploads and downloads, request and response bodies use JSON.

## Base URL

All documented paths use the global `/api` prefix. Use the production or staging host supplied by Gomobile.

Set the complete base URL once in your shell:

```bash
export GOMOBILE_API_BASE_URL="https://<your-assigned-host>/api"
export GOMOBILE_API_KEY="<your-api-key>"
```

Examples in this reference use those variables. Replace the placeholder host and key before running them.

## Authentication

Send the API key on every documented request:

```http
X-API-Key: <your-api-key>
```

For JSON bodies, also send:

```http
Content-Type: application/json
```

API keys can have the **Admin**, **Manager**, or **Agent** role. Most endpoints in this reference accept any of those API-key roles. An endpoint marked **Admin** rejects Manager and Agent keys. Available operations also depend on your organization’s enabled services.

## Pagination

Most list endpoints use page-based pagination:

| Parameter | Meaning | Default | Limit |
| --- | --- | --- | --- |
| `page` | One-based page number | `1` | Minimum `1` |
| `limit` | Items per page | `20` | Maximum `100` |
| `search` | Text search where supported | — | Maximum 100 characters |
| `sortBy` | Endpoint-specific sort field | Endpoint-specific | Use endpoint-supported fields |
| `sortOrder` | Sort direction | Endpoint-specific | `asc` or `desc` |

A paginated response has this envelope:

```json
{
  "data": [],
  "meta": {
    "page": 1,
    "limit": 20,
    "total": 0,
    "totalPages": 0,
    "hasNextPage": false,
    "hasPreviousPage": false
  }
}
```

Contact interactions use cursor pagination instead. Follow the returned `meta.nextCursor` rather than constructing a cursor yourself.

## Validation

Gomobile rejects undocumented request properties. Send only documented fields. UUID path and body fields must contain valid UUIDs, and ISO timestamps must include a valid timezone or UTC marker when the endpoint requires a date-time.

## Errors

Use the top-level `code` as the machine-readable discriminator. Handle errors using `code` and, when present, `fieldErrors` or `fieldDetails`. Descriptive `message` and `error` values can vary between error types.

```json
{
  "code": "VALIDATION_FAILED",
  "fieldErrors": {
    "primaryPhone": ["primaryPhone must be longer than or equal to 3 characters"]
  },
  "fieldDetails": {
    "primaryPhone": [
      {
        "code": "minLength",
        "params": { "min": 3 }
      }
    ]
  },
  "statusCode": 400,
  "message": "Validation failed",
  "error": "BAD_REQUEST",
  "timestamp": "2026-10-01T10:00:00.000Z",
  "path": "/api/contact"
}
```

Common HTTP statuses:

| Status | Meaning |
| --- | --- |
| `400` | Invalid request or referenced input |
| `401` | Missing, invalid, expired, disabled, or revoked key |
| `403` | The key role or enabled services do not permit the operation |
| `404` | Resource does not exist in the key's organization |
| `409` | Duplicate resource, state conflict, or blocked lifecycle transition |
| `402` | Insufficient organization credits (`INSUFFICIENT_CREDITS`); check the balance and arrange additional credits through your Gomobile contact |
| `422` | A domain rule prevented the operation |
| `429` | A rate-limited route rejected the request; obey `Retry-After` |
| `500` | Unexpected server error |

The API can return `Retry-After`, `X-RateLimit-Limit`, `X-RateLimit-Remaining`, and `X-RateLimit-Reset` on rate-limited routes. Use the headers returned for the requested operation to handle throttling.

## Versioning and idempotency

To avoid duplicate work when retrying requests:

- a repeated `POST` can create or trigger work again;
- use returned resource IDs to follow the original operation;
- do not retry a timed-out mutation automatically without first checking its result.

Handle unfamiliar response values without assuming they have the same meaning as existing ones.

The Contacts API is organization-scoped. Admin, Manager, and Agent API keys can use the endpoints on this page.

<Warning>

## Contact schema

Create requests require `primaryPhone`. Optional properties are:

```json
{
  "primaryPhone": "+212600000000",
  "firstName": "Sara",
  "lastName": "Test",
  "fullName": "Sara Test",
  "primaryEmail": "sara.test@example.com",
  "address": "Example address",
  "city": "Casablanca",
  "state": "Casablanca-Settat",
  "zip": "20000",
  "occupation": "Example role",
  "preferredChannel": "phone",
  "gender": "female",
  "channels": [],
  "customAttributes": {
    "customer_tier": "test"
  }
}
```

String limits are enforced by the API: names are at most 64 characters, phone numbers at most 20, addresses at most 256, and email values must be valid. Unknown request properties are rejected.

A contact response includes `id`, `organizationId`, the contact fields, `channels`, `createdAt`, and `updatedAt`. `GET /contact/:id` also includes typed `customAttributes` entries.

## List contacts

`GET /contact`

Query parameters: `page`, `limit`, `search`, `sortBy`, `sortOrder`, and `include`. Search covers name, phone, and email fields. Supported sort fields are `firstName`, `lastName`, `primaryPhone`, `primaryEmail`, and `createdAt`. Pass `include=customAttributes` to embed attribute values.

```bash
curl --get "$GOMOBILE_API_BASE_URL/contact" \
  -H "X-API-Key: $GOMOBILE_API_KEY" \
  --data-urlencode "page=1" \
  --data-urlencode "limit=20" \
  --data-urlencode "search=Sara" \
  --data-urlencode "include=customAttributes"
```

Response: `200` with the standard `{ data, meta }` pagination envelope. This request does not change data.

## Get a contact

`GET /contact/:id`

Path parameter: `id`, a contact UUID.

```bash
curl "$GOMOBILE_API_BASE_URL/contact/$CONTACT_ID" \
  -H "X-API-Key: $GOMOBILE_API_KEY"
```

Response: `200` with the contact and its custom attributes. Returns `404` when the contact is not present in the API key's organization.

`POST /contact`

## Bulk upsert contacts

## Import contacts

Contact ingestion is a four-request workflow. This import workflow validates Moroccan phone numbers; use an accepted `+212` or local Moroccan format and confirm support before importing international numbers. It accepts CSV, XLSX, and XLS files and can optionally link successfully processed contacts to a static audience.

### 1. Upload

`POST /contact/ingestion/upload`

Multipart fields: `file`, optional `previewRows`, optional `hasHeaderRow`, and optional `audienceId`.

```bash
curl -X POST "$GOMOBILE_API_BASE_URL/contact/ingestion/upload" \
  -H "X-API-Key: $GOMOBILE_API_KEY" \
  -F "file=@contacts.csv" \
  -F "hasHeaderRow=true" \
  -F "previewRows=20"
```

Response: `201` with `sessionId`, file metadata, detected columns, preview rows, and `expiresAt`. Side effect: uploads customer data and creates a temporary ingestion session. Files must not exceed 50 MiB or 100,000 rows, including a header row if present. `previewRows` defaults to `20` and accepts 1–100. `hasHeaderRow` defaults to `false`; set it to `true` when the first row contains column names. Sessions expire after 30 minutes of inactivity; upload and validate again if expired.

### 2. Validate mappings

`POST /contact/ingestion/validate`

```bash
curl -X POST "$GOMOBILE_API_BASE_URL/contact/ingestion/validate" \
  -H "X-API-Key: $GOMOBILE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "sessionId": "'"$INGESTION_SESSION_ID"'",
    "columnMappings": [
      { "column": 0, "field": "firstName" },
      { "column": 1, "field": "primaryPhone" },
      { "column": 2, "field": "custom.customer_tier" }
    ]
  }'
```

Response: `201` with valid, invalid, and existing counts plus previewed rows. Exactly one column must map to `primaryPhone`. Duplicate phones inside the same file are validation errors; a phone matching an existing contact is shown as an update candidate.

### 3. Page through validation results

`GET /contact/ingestion/validate/:sessionId`

Query parameters: `page`, `limit` (default `50`, maximum `500`), and `filter` (`all`, `valid`, `invalid`, or `existing`).

```bash
curl --get "$GOMOBILE_API_BASE_URL/contact/ingestion/validate/$INGESTION_SESSION_ID" \
  -H "X-API-Key: $GOMOBILE_API_KEY" \
```

## Live-audience rule schema

A live audience requires a rule group. Groups use `AND` or `OR`. Maximum rule-tree depth is three, counting the root group and condition nodes. A root group containing a subgroup containing conditions reaches this limit; another subgroup would exceed it.

```json
{
  "type": "group",
  "operator": "AND",
  "children": [
    {
      "type": "condition",
      "attributeName": "contact.city",
      "operator": "equals",
      "value": "Casablanca"
    },
    {
      "type": "condition",
      "attributeName": "custom.customer_tier",
      "operator": "equals",
      "value": "test"
    }
  ]
}
```

Operators: `equals`, `not_equals`, `is_empty`, `is_not_empty`, `gt`, `gte`, `lt`, `lte`, `contains`, and `not_contains`. Comparison operators are limited to compatible types; `contains` is for text-like fields. `is_empty` and `is_not_empty` take no value.

| --- | --- | --- | --- |
| `POST` | `/flows` | Create a flow | Creates automation configuration |
| `GET` | `/flows` | List flows | None |

| `PUT` | `/flows/:id` | Update a flow | Changes future executions |
| `DELETE` | `/flows/:id` | Soft-delete a flow | Destructive configuration change |
| `GET` | `/flows/:id/run-inputs` | Inspect required contact values | Reads contact data |
| `POST` | `/flows/:id/run` | Start an asynchronous run | Can call, message, change contacts, and consume credits |
| `POST` | `/flows/executions/:id/cancel` | Cancel a run and queued retries | Can hang up a live call |
| `GET` | `/flows/:id/executions` | List one flow's runs | Reads activity and contact data |
| `GET` | `/flows/executions/:id` | Get a run report | Reads activity, variables, messages, and costs |
| `GET` | `/flows/:id/funnel` | Get a flow funnel snapshot | Can enqueue report computation |

See the [endpoint catalog](/developers/reference/endpoint-catalog) for resource references and support scope.

## Flow schema

A flow requires:

- `name`, up to 255 characters;
- `startNodeId`, which must exist in `nodes`;
- `nodes`, a map keyed by node ID; and
- optional `channelType` and `status`.

Customer-facing flow types map to API channel types:

| Product term | API value |
| --- | --- |
| Multichannel flow | `agnostic` |
| Voice flow | `call` |

Create `call` or `agnostic` flows. SMS and WhatsApp messages are actions within these flows; standalone SMS- or WhatsApp-typed flows are not supported.

Statuses are `draft`, `active`, and `archived`. A status is lifecycle metadata; it does not by itself prove that a graph is safe to execute.

Each node has this base structure:

```json
{
  "id": "apply-tag",
  "type": "tag",
  "config": { "tagName": "api-test" },
  "outputs": {}
}
```

The allowed node types and configuration depend on `channelType`. Unknown node types, invalid configuration, broken edges, or a missing start node are rejected.

## Transfer recording and sub-flow variables

The Voice `forward` step uses `record` for its bridged-conversation segment recording. Recording defaults to enabled when this field is omitted, and ringing is not recorded. Set `record: false` deliberately when recording should be disabled; this control is separate from full-call recording. `ringTimeoutSec` defaults to 30 seconds (5–120 accepted). Optional `maxDurationSec` accepts 10–7,200 seconds; omitting it leaves bridged duration uncapped.

The Multichannel `invoke_sub_flow` configuration’s `varMapping` field currently has no effect. Do not rely on it to restrict propagation or isolate sensitive variables.

```bash
    "status": "draft",
    "startNodeId": "apply-tag",
    "nodes": {
      "apply-tag": {
        "id": "apply-tag",
        "type": "tag",
        "config": { "tagName": "api-test" },
        "outputs": {}
      }
    }
  }'
```

The schedule dates below are illustrative. Replace them with future timestamps before submitting a request; never reuse an example date without reviewing when the campaign will activate.

`name`, `flowId`, and `audienceId` are required. A Voice (`call`) flow requires `dialConfig`. A Multichannel (`agnostic`) flow can require it when it invokes a Voice sub-flow.

`dialConfig.didIds` accepts 1–100 active numbers available to the organization. `timeoutMs` is 5,000–120,000 milliseconds. Recording is optional and must be used only with appropriate notices and consent.

Retries are supported for eligible call campaigns:

- `fixed_delay`: `delayMs` up to 86,400,000 and `maxAttempts` from 1–10, including the initial attempt.
- `scheduled`: `scheduledTimes` contains 1–9 strictly increasing ISO timestamps. The first entry schedules attempt 2; total attempts equal the number of entries plus the initial attempt, up to 10.

Busy, rejected, and unanswered calls are eligible for retry while the attempt budget permits. Answered calls are not retried. `retryOnVoicemail` defaults to `true` and applies when answering-machine detection is enabled; set it to `false` to avoid repeated voicemail attempts. Campaign retry policies apply to Voice campaigns, not Multichannel campaigns.

Campaign calling policy is resolved and stamped at activation. Review your organization’s calling hours before activation.

## Calling policy

`callingPolicy` is a top-level field on campaign creation and draft updates. Weekly hours use the organization’s timezone; do not supply a timezone inside this request.

| Setting | Behavior |
| --- | --- |
| Omit `callingPolicy` or send `null` | Inherit the organization’s default at activation |
| Supply `callingPolicy` | Replace the default with this campaign’s complete policy; weekdays are not merged |
| Neither organization nor campaign has a policy | Contact hours are unrestricted; the campaign schedule still applies |

Sending `null` does not override an existing organization policy with unrestricted hours. The effective policy is resolved when the campaign becomes active; later organization-default changes do not alter it.

`callingPolicy.window` uses weekday keys `sunday` through `saturday`, each containing arrays of `{from, to}` spans:

- Times use 24-hour `HH:mm`; `from` is inclusive and `to` is exclusive.
- Each span must have `from < to`. Omitted weekdays are closed.
- At least one weekday must contain hours. Up to eight spans are accepted per weekday.
- A span cannot cross midnight. Configure separate permitted spans on consecutive weekdays.
- Optional `blackouts` accepts up to 100 `{from, to, label?}` entries. Timestamps require `Z` or a UTC offset; labels are at most 120 characters. Choose a `to` later than `from`.

This draft update permits contact Monday through Friday from 09:00 to 17:00, with a synthetic blackout. Replace the blackout dates before use, or omit `blackouts` if no blackout is needed:

```bash
curl -X PATCH "$GOMOBILE_API_BASE_URL/campaigns/$CAMPAIGN_ID" \
  -H "X-API-Key: $GOMOBILE_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "callingPolicy": {
      "window": {
        "monday": [{ "from": "09:00", "to": "17:00" }],
        "tuesday": [{ "from": "09:00", "to": "17:00" }],
        "wednesday": [{ "from": "09:00", "to": "17:00" }],
        "thursday": [{ "from": "09:00", "to": "17:00" }],
        "friday": [{ "from": "09:00", "to": "17:00" }]
      },
      "blackouts": [{
        "from": "2030-12-24T09:00:00+01:00",
        "to": "2030-12-24T17:00:00+01:00",
        "label": "Synthetic test closure"
      }]
    }
  }'
```

Review the resulting policy before activation. These hours govern contact initiation; an existing live call can continue outside them. They do not establish legal compliance.

## Monitor processing

`GET /knowledge-bases/:kbId/documents/:docId`

```bash
curl "$GOMOBILE_API_BASE_URL/knowledge-bases/$KB_ID/documents/$DOCUMENT_ID" \
  -H "X-API-Key: $GOMOBILE_API_KEY"
```

Document status progresses through values including `uploading`, `waiting_for_scan`, `processing`, and `ready`. Terminal problems are `failed` or `blocked`. While processing, `processingStep` can be `parsing`, `chunking`, `embedding`, or `upserting`.

Stable failure reasons are:

- `scan_blocked`: malware scanning refused the file; it cannot be retried;
- `scan_unavailable`;
- `unsupported_content`;
- `no_extractable_text`; and
- `indexing_error`.

Do not poll aggressively. Back off between reads and stop at `ready`, `failed`, or `blocked`.

```bash
  --data-urlencode "limit=20"
```

`PUT /whatsapp/templates/:id` resubmits a rejected template’s complete revisable content. `category`, `bodyText`, and `variables` are required. Include any header, footer, and buttons you want to retain; omitting them removes that content. The template’s name and language cannot be changed. A template that is not rejected returns `409`.

```bash
curl -X PUT "$GOMOBILE_API_BASE_URL/whatsapp/templates/$TEMPLATE_ID" \
  -H "X-API-Key: $GOMOBILE_API_KEY" \
  -H "Content-Type: application/json" \

    "category": "UTILITY",
    "bodyText": "Hi {firstName}, your revised test update is ready.",
    "variables": [
      { "name": "firstName", "fallback": "there" }
    ],
    "footerText": "Appointment reminder",
    "buttons": [{ "type": "QUICK_REPLY", "text": "Acknowledged" }]
  }'
```

```bash
curl -i -X DELETE "$GOMOBILE_API_BASE_URL/whatsapp/templates/$TEMPLATE_ID" \
  -H "X-API-Key: $GOMOBILE_API_KEY"
```

## Send a test

`POST /whatsapp/templates/:id/send-test`

```bash
curl -X POST "$GOMOBILE_API_BASE_URL/whatsapp/templates/$TEMPLATE_ID/send-test" \
```

Example `200` response:

```json
{ "messageId": "provider_message_id" }
```

# Gomobile documentation

Customer-facing product guides and API reference, built with Mintlify.

## Requirements

- Git and access to this GitHub repository.
- [Node.js](https://nodejs.org/) **20.17.0 or newer**, with npm. Use a supported LTS release.
- Internet access for downloading the Mintlify CLI and preview files.

Check your installation:

```bash
node --version
npm --version
```

You do not need the Gomobile application repository, a database, or API credentials to preview the documentation.

## Clone and preview

Run these commands in your terminal:

```bash
git clone https://github.com/Gomobile-Africa/product-docs.git
cd product-docs
npx mint@latest dev
```

If npm asks to install `mint`, confirm the installation. Keep the terminal running, then open **http://localhost:3000** in your browser. If that port is occupied, open the URL printed in the terminal instead.

Run the preview command from the repository root, where `docs.json` is located. Edit an `.mdx` page and save it to see the preview update. Stop the server with **Ctrl+C**.

For subsequent sessions:

```bash
cd product-docs
npx mint@latest dev
```

Use the path where you cloned the repository if your terminal is in a different directory.

## Edit the documentation

| Location | Content |
| --- | --- |
| `docs.json` | Site settings and navigation |
| `index.mdx` | Documentation homepage |
| `product/`, `learn/` | Product overview and concepts |
| `getting-started/`, `quickstarts/`, `guides/` | Setup instructions and task guides |
| `developers/` | API documentation |
| `assets/`, `custom.css` | Images, branding, and styling |
| `discovery/` | Internal decisions; not customer documentation |

See [CONTRIBUTING.md](CONTRIBUTING.md) before changing content.

## Check changes

From the repository root, run:

```bash
npx mint@latest validate
npx mint@latest broken-links
```

Fix reported errors before opening a pull request. These commands check the documentation; they do not test the Gomobile API examples against a running backend.

## Troubleshooting

- **`node` or `npm` not found:** install Node.js, then reopen your terminal.
- **Clone fails:** confirm your GitHub account has repository access and Git authentication is configured.
- **Preview cannot find `docs.json`:** change into the cloned `product-docs` directory.
- **Port already in use:** use `npx mint@latest dev --port 3333`, then open http://localhost:3333.
- **Downloads fail:** check your internet connection, proxy, or VPN. Mintlify preview downloads may require access to `releases.mintlify.com`.

For CLI setup details, see the [Mintlify installation guide](https://www.mintlify.com/docs/cli/install).

# Contributing

Write customer documentation in English using Gomobile terminology: contacts, static/live audiences, flows, campaigns, runs, calls, inbound bindings, and credits.

## Verify content

- Check the target release’s customer UI in `apps/web` and behavior in `apps/backend`. Treat the Gomobile repository as read-only.
- Verify permissions, request/response shapes, errors, prerequisites, and side effects. Test workflows when source inspection alone cannot establish the result.
- Document customer-facing features. Keep internal, private, disabled, and unreleased capabilities out of customer pages.
- Record unknown release, API, or policy decisions in `discovery/publication-review-list.md`. Code presence alone does not establish public support.
- Do not invent limits, pricing, retention, compliance, or compatibility guarantees.

## Write useful pages

Task pages should explain the outcome, prerequisites, numbered steps, expected result, limitations, troubleshooting, and next task. Keep labels aligned with the English UI.

Use synthetic data and test numbers you control. Never expose customer data or credentials. Screenshots need meaningful alt text and written instructions.

API examples must match the documented endpoint, use server-side `X-API-Key` authentication, and identify calls, messages, data changes, or credit use. Use the API host supplied by Gomobile; never infer support from raw Swagger or successful authentication.

## Validate changes

```bash
mint validate
mint broken-links
```

Check changed workflows, headings, examples, mobile layout, keyboard access, and contrast as relevant.
